# WAPF capability ledger

This is OPF's acceptance ledger for replacing WAPF Free, Pro, Extended, and
the six current official add-ons. Each ID is a stable evidence/fixture key;
fixture declarations alone do not prove behavior or lifecycle coverage.
`baseline supported` is evidence from the 2026-09-19 OPF replacement plan,
not a public parity claim. `supported` requires executed behavior evidence;
`partial` means some behavior exists but a material path remains unproven or
unsupported. `gap` is known absent in the baseline; `needs audit` has no
established result. Declarative fixtures are useful inputs, not execution
evidence.

WAPF's current paid edition names are Pro, Extended, and Extended + Addons;
official documentation does not define a separate current edition called
"Premium." The target here is the Extended edition: Pro core plus Extended
features. The separate add-ons and Extended + Addons bundle are excluded from
this 1.0 parity gate unless the user expands scope. Official documentation
says add-ons may be purchased separately.

## Progress snapshot and release goalposts — 2026-10-02

Scope baseline: the live site has WAPF Extended 3.1.5 installed (inactive),
but Studio Wombat's current official changelog lists Extended 3.2.1. Extended
includes Pro; six separately sold add-ons are outside this Extended-edition
target and remain separately tracked. The ledger has 138 rows: 132 for the
Free + Pro + Extended edition scope (including 3 “All versions” rows), and 6
for separately sold add-ons. Of the 132 edition rows, 2 are baseline-supported,
8 supported, 8 supported with a documented difference, 113 partial, and 1
known gap. Percentage coupon scope advanced from gap to partial in public
commit `f03979d`; its implementation and current proof are recorded in
[coupon scope evidence](coupon-scope-proof.md). The 28 Extended-only
rows comprise 0 supported, 4 supported with a
documented difference, 24 partial, and no known gaps. These are row counts, not weighted
feature percentages; gate completion is the progress measure. The paragraph
HTML slice also maps WAPF Extended `p` content, applies its restricted HTML
allowlist, supports optional WordPress shortcode processing, and preserves the
payload on WAPF JSON/WXR export. Live WAPF runtime proof remains pending.

The current swatch audit reconciled `WAPF-FIELD-SWATCH-COLOUR` from supported
with a documented difference to partial: the prior claim had no renderer,
builder, or WAPF mapper evidence in OPF. This increment adds those paths and
unit coverage; runtime parity evidence remains pending.

The available-source audit is complete: it covers installed Extended 3.1.5
(bundled Pro), public Free 1.7.1 source, the current tier/marketing pages, and
every published Extended 3.1.6–3.2.1 and Pro 3.2.2 changelog change. The
release-by-release crosswalk is in `WAPF-EXTENDED-3.1.5-SOURCE-AUDIT.md`.
Exact internals that public release notes do not specify remain named in the
affected capability rows; they do not hold up unrelated implementation.
Continue against the audited code and public contract, and keep any unresolved
setting key or behavior explicit instead of guessing it.
The category child-product price-type row is source-verified against installed
3.1.5 code: category queries expose `fixed` (catalog price) or `none` (zero
price); quantity selectors use the selected child quantity. OPF category
price-type mapping/equivalence remains a parity gap until proved. See the
[ordered OPF 1.0 roadmap](OPF-1.0-ROADMAP.md) for work packages and gate rules.

decomposed into sized implementation and verification tasks.

## Promotion rule

The registry's `supported_flows` values describe intended coverage only. A
status promotion requires executable tests for the relevant behavior through
storefront rendering, submission, server-calculated pricing, classic cart,
block cart/checkout, order storage, order email/meta, and order-again, as
applicable. Migration tests must also prove that unsupported source data blocks
publication with an actionable report, never silent data loss. Schema
normalization and fixture-shape validation alone cannot promote a status.
